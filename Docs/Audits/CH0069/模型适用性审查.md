## 实际文件检查

- 校验 `Diagnostics/checksums.sha256` 中 395 个文件：无缺失、无哈希不匹配。主 GLB 哈希与清单一致。
- GLB 有 187 个节点、3 个网格、3 组蒙皮、6 个预览材质、5 张内嵌图片及 33 个动画。
- 可渲染部分为身体、武器及备用弹匣；共 10,753 个三角形。没有手册规定的三角形预算，不能仅凭此数认定运行性能已达标。
- 身体蒙皮使用 141 个关节，武器 4 个，备用弹匣 1 个。检查未发现越界关节索引、零权重顶点或明显权重归一化问题。
- 所有 33 个主动画的时间序列、目标节点、输出数量及有限数值检查通过。独立动画 GLB 的节点名称与主模型一致。
- Blender 成功建立 33 个 Action；选择 Cafe_Walk 后采样，7,353 个身体网格顶点发生位移，最大约 0.329 个导入场景单位。这证明原动画能实际驱动网格，不代表所有极端姿态均已做视觉验收。
- Blender 将各蒙皮骨骼合并为 146 个骨骼的 Armature。glTF 导入器另生成骨骼显示辅助网格，测试导出脚本已排除该辅助网格。
- Unity 原动画 FBX 导入后仍有 3 个 SkinnedMeshRenderer、33 个 Animation Clip、10,753 个三角形及有效 Generic Avatar。Unity 顶点数量可能因法线、UV 等拆分变化，不能与 GLB 顶点数直接比较作为损坏依据。
- 新动作 `Bip001|Audit_CustomHeadTurn` 导入 Unity 后长度为 1 秒，具备 1,470 条动画曲线。对测试模型及原模型分别采样，头部旋转变化均约 7.74°，证明新 Clip 与原模型骨骼绑定兼容。

## 正式制作前需要处理的缺口

**1. 光环没有进入主 GLB 的可渲染网格。**

主 GLB 保留 `HaloRoot / CH0069_Halo` 节点，但该节点未绑定 mesh。包内 `Metadata/meshes.json` 存在 94 顶点的 CH0069_Halo 几何记录，Geometry 与光环 PNG 也存在，因此可优先从包内恢复几何、节点挂接和材质，而不必直接判断整个源资源不可用。正式版本需验证光环能显示并跟随角色。

**2. 预览材质不等于最终卡通材质。**

`manifest.json` 明确声明主 GLB 的 `role=preview`、`modelMaterialMode=preview`，Materials JSON 才是权威材质来源。GLB 仅含基础颜色贴图，未完整还原原 MX Shader 的卡通光照、发丝高光、遮罩、光环发光和嘴部图集效果。Shader JSON 是提取快照，不能当作现成可编译的 Unity Shader。

角色 Body、Hair、Face、EyeMouth、Eyebrow、Weapon、Halo 的核心贴图引用均已导出；Hair 的 `_TempTex` 在源中不存在，不应当作贴图丢失。整包有 117 个 unresolved-external 贴图属性引用，主要涉及附带特效；不能把它们都归为角色核心贴图缺失。V1 若不使用原战斗特效，可先只处理角色实际使用的材质。

**3. 嘴部表情需要单独恢复。**

在范围内的网格没有 BlendShape，手册也未强制要求 BlendShape，因此不因此判定模型不可制作。眼部和眉部骨骼可用于表情编辑；嘴部依赖 `Character_Mouth.png` 的 8×8 图集。主 GLB 的扩展元数据保留 51 个 `SetMouthTile` 事件、3 个 `AniEvt_InstantiateFx` 事件，但它们不是标准 glTF 骨骼动画通道，普通 Blender→FBX 流程不能据此认为 Unity 自动恢复了事件。

正式流程应从动画元数据建立嘴部图集切换逻辑或重建 Animation Event。特效实例化事件按项目需要重新映射或过滤，避免引用未实现的游戏脚本。

**4. 桌宠动作和运行时状态机需要制作。**

手册第 28 节列出的八类额外动作尚未正式提供。可以先预览 Cafe_Idle、Formation_Idle、Cafe_Walk、Cafe_Reaction、Victory 等原素材；这些只是复用候选，不应只根据名称直接认定满足 Thinking / Working / Success 等状态。新动作制作必须保留骨骼名称和层级，完整动作预先烘焙，Animation Rigging 负责 LookAt 等小幅约束。

原 Animator 的 base controller 有包外未解析依赖，不能直接当作桌宠状态机使用。循环标记在现有动画清单中为 unavailable-in-source，需在 Unity 中检查 Idle/Walk 的首尾并配置 Loop Time。正式导出应固定 30 FPS 与源动画采样率匹配，禁用额外叶骨，明确动作命名和 Generic 根节点，再验证根位移，防止拖拽和 LookAt 与动画互相干扰。

**5. 提取成功不等于项目验收通过。**

`extraction_report.json` 的 PASS 证明提取流程通过其自身检查；它不验证桌宠状态映射、画面还原、透明窗口互动或 Unity 场景功能。原始 GLB 为源资产，最终应用按手册导出 Unity Runtime Asset，无须默认增加运行时 GLB 加载依赖。

手册还要求 Legal GLB Source。provenance.json 记录来源与提取过程，未提供使用授权证明；合法使用与分发条件需由资源权利说明确认。本审查未对权利状态作通过判断。

## 交付顺序与证据

建议先恢复光环与核心卡通材质，再固定 30 FPS 的 Blender→FBX→Unity Generic 流程，然后制作桌宠动作和 character_manifest.json，最后接入 Animator、触摸区域、拖拽与 LookAt 并做场景验收。原始 Material/CH0069 文件保持不变。

审查目录中的 `CH0069_original_probe.fbx` 和 `CH0069_custom_probe.fbx` 仅用于验证导入和新动作绑定，不是完成材质、光环、状态机和优化后的正式交付资产。

- `structural_audit.json`：文件校验、蒙皮和动画结构检查。
- `blender_audit.json`：Blender 对象、骨骼、Action 与行走形变实测。
- `unity_audit.json`：Generic Avatar、原动画数量和测试新动作的 Unity 实测。
- `unity_probe.log`：Unity 检查日志。
- `Tools/AssetPipeline/audit_ch0069_blender.py`：Blender 检查与 FBX 测试导出脚本。
- `Tools/AssetPipeline/CH0069UnityAudit.cs`：Unity 导入与新动作绑定检查脚本。

软件流程核对：[Blender glTF 导入导出说明](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)、[Unity Generic 动画导入说明](https://docs.unity3d.com/6000.0/Documentation/Manual/GenericAnimations.html)、[Unity 外部动画导入说明](https://docs.unity3d.com/6000.0/Documentation/Manual/AnimationsImport.html)。这些文档支持流程选择，模型可用性结论主要来自本地实测。
