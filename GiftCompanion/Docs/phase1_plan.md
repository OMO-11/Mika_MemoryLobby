# Phase 1：Core 阶段方案

2026-10-12。状态：**用户已批准，已按 1A → 1B → 1C → 1D 顺序完成并验收通过**。依据《项目总宪法》第 4—9、21—22、41—43、49、51 节与当前主工程。Phase 0 六项技术链均已实测通过，记录见 `phase0_status.md`；本方案不把独立探针通过等同于业务服务已经完成。实际交付与证据见 `phase1_status.md`。下文保留批准时的实施设计。

## 阶段目标

把现有可运行骨架变成可靠的共享核心：启动能恢复短期状态，两个模式使用同一个角色与数据库，统一调用 DeepSeek，切换与退出时正确取消任务、保存状态和释放资源。

宪法主验收路径保持为 **Home → Companion → Home → AgentPet → Home，连续切换不崩溃**。在此基础上增加真实持久化、统一 LLM 调用和异常流程的证据。启动始终进入 Home，不按上次模式直接进入透明桌宠。

## 执行顺序与检查点

### 1A：配置、日志与正式数据库

先完成基础服务，不改最终 UI。

- 沿用 Unity 6000.3.7f1、Built-in / Gamma / D3D11 和纯 C# Core，不引入服务框架或新的 ORM。
- 普通设置放在 `UserData/Config/settings.json`，仅包含模型、超时等非秘密字段。默认仍为 `deepseek-flash`、30 秒；校验格式和范围。损坏配置保留供诊断，使用明确的默认值；保存采用临时文件与替换，避免半写文件。
- 身份只从只读 `identity.json` 加载，记忆和模型均不能改写。现有空白 persona / relationship 保持空白，不代填角色经历或关系。
- Key 继续由 LocalSecrets 读取环境变量或 Windows 用户级 DPAPI 文件。现有配置脚本只写编辑器工程目录：本阶段补充明确的 Editor / Player 目标，默认不在两处静默复制 Key。验收 Player 时使用同一 Windows 用户按目标目录配置或使用已支持的环境变量；Key 不随构建分发。
- Editor 使用工程 `UserData/`；Player 使用 `%LOCALAPPDATA%/GiftCompanion/`。各自内部只有一个正式 `memory.db`，两个模式共享同一 DatabaseService。阶段探针数据库继续独立保留，不复制或导入正式库。
- 复用已验证的 SQLite 原生依赖与必要的底层代码，建立正式 schema v1：本阶段只建 `app_state`，保存状态版本、角色 ID、状态 JSON 与更新时间。`messages`、`sessions`、FTS5 等在 Phase 2 的后续迁移中加入，不提前创建完整 Memory 系统。
- 写入统一串行，使用参数绑定和事务；读取返回独立快照。迁移有明确版本与事务边界，已有库迁移前备份，遇到更高版本拒绝打开写入。数据库损坏或不可写时不静默退回 RAM 冒充保存成功。
- 日志记录启动、迁移、切换、请求 ID / 来源 / 耗时 / 结果、错误类型与退出。日志不包含 Key、请求头、完整对话、短期话题正文或剪贴板。

**检查点：** 新库创建、已有库重开、状态原值恢复、迁移失败不半升级、不可写时明确失败；Editor / Player 数据路径与 Key 目标可区分。完成后更新日志与验收记录，再进入 1B。

### 1B：LLMService 与 CharacterCore 的最小文字链

调用路径固定为：验收入口 → CharacterCore → LLMService → DeepSeekApiClient。场景、UI 和表现适配器不直接访问 HTTP 或数据库。

- AppRoot 持有并释放唯一 LLMService / HTTP 客户端，将本地 Key、模型和超时注入服务。Key 缺失不阻止素材与 Home 运行，但文字请求返回明确的不可用结果。
- 保留 `SendMessageAsync` 的最终结果用途，增加 Core 的流式调用契约，复用 `LLMChunk`；单条请求能够逐段消费并确认最终完成。不增加全局事件总线，场景订阅随自身生命周期退出。
- 两个模式共享身份与状态，仅 `InteractionSource` 标记不同。先使用已配置身份和当前输入构成最小请求；近期历史、长期记忆检索及正式 PromptBuilder 留到 Phase 2。
- 同一时刻只允许一条角色请求；重复提交返回忙碌结果，不排队发送多个请求。请求绑定应用、模式和调用者取消令牌；退出旧模式后不再把旧片段写入新场景。
- 收到完整 `[DONE]` 才计为成功并更新 `LastInteractionAt`。取消或截断的片段不当成完整成功回复；Core 不通过文本猜测并改写人物身份、话题或情绪。
- 超时、401、429、网络失败、流截断分别映射为稳定错误代码；默认不自动重试，避免额外计费或重复内容。日志只有状态与计数，技术错误不直接显示在沉浸主画面。
- 使用显式启用的开发验收入口发送短请求，验证 Core 确实消费流式结果。此入口不制作正式聊天面板，不作为用户聊天历史，不自动触发语音或工具。

**检查点：** 通过正式 Core / LLMService 完成一次真实短请求；离线可控响应覆盖取消、超时、HTTP 错误和截断。当前已完成的 Phase 0 直连接口验收不能替代这一项。

### 1C：切换、恢复与退出

- 启动顺序保持：单实例检查 → Logger → Config → Database → Migration → 恢复 CharacterState → 装配共享服务 / Core → Home。启动失败不留下可操作的半初始化场景；保留简短失败反馈与脱敏日志。
- 切换顺序设计为：预检目标场景 → 暂停新提交 → 取消并等待旧请求收尾 → 生成目标状态快照 → 事务保存 → 提交逻辑模式 → 加载目标场景。重复点击仍不排队。
- `LastMode` 统一表示最近成功提交的目标模式。快照先设置目标值再落库，保存成功后才替换可见字段，修正当前“保存旧值后才更新 LastMode”的骨架语义；不替换共享 CharacterState 对象。
- 取消只在提交边界前生效；保存失败或提交前取消保留原场景 / 原状态并解除暂停。事务提交后完成目标场景激活，避免把已经落库的模式当作未发生。Unity 激活无法真正取消，不将取消令牌当成撤销操作。
- 加载失败进入明确的 Home 恢复流程并同步逻辑模式与持久状态，记录故障；恢复也失败则停止交互并给出简短提示，不继续运行不一致的两套场景。
- 沿用已验证的 Spine / 3D 适配器与同一窗口模式切换。离开场景清理触摸、订阅和该模式令牌，不能删除或重建 AppRoot 及共享服务。
- 显式退出先停止接收请求、取消并收尾、保存最后状态，再关闭数据库 / HTTP / 日志、释放 Mutex。系统关闭提供有界收尾与尽力保存；不承诺强制杀进程后保留最后一瞬的内存变化。

**检查点：** 切换与退出期间无旧请求回调访问已销毁场景；保存失败时仍可留在原模式重试；重启恢复状态但进入 Home；资源无重复创建或释放后继续使用。

### 1D：集成验收与阶段交付

| 验收 | 通过条件 | 证据 |
| --- | --- | --- |
| 宪法主路径 | Home → Companion → Home → AgentPet → Home 连续 3 轮；唯一 AppRoot / Core / State / Database / LLM，无未处理异常 | PlayMode Smoke Test |
| 短期状态持久化 | 写入测试状态，关闭重开仍保留 mood / energy / topic / 时间；启动进入 Home，模式记录语义一致 | 纯逻辑持久化测试与独立测试库 |
| 保存 / 迁移故障 | 失败不半升级、不静默换 RAM；切换前保存失败不离开原模式 | 定向故障测试 |
| 统一文字链 | 从正式 Core 经 LLMService 获得真实 Streaming 和最终完成；只记计数及耗时 | 显式开发 Probe 与脱敏 JSON |
| 请求取消 | 请求中返回 Home、退出或调用者取消，旧请求收尾且无新场景残留片段；下一请求可正常开始 | 可控流测试及少量场景测试 |
| 配置 / 无 Key | 非秘密设置重启后生效；无 Key / 无网仍可进入 Home 和播放素材，文字请求清楚失败 | 配置测试与启动检查 |
| Windows Player | 新构建在 Player 数据目录工作，正式 Core 请求与状态重开通过；透明桌宠 / Home 窗口恢复不退化 | Windows EXE 报告 |

纯逻辑重点验证事务、状态提交与取消竞态；场景使用少量 Smoke Test，不为简单映射编写大批镜像测试。真实 API 只做必要短请求，错误分支用可控响应，避免重复联网消耗。

阶段产物：正式服务代码、必要测试、`Docs/Validation/Phase1/` 实测记录，以及更新后的架构、两级 README、阶段状态和开发日志。只有验收实际通过才将 Phase 1 标为完成。

## 阶段边界

Phase 2 才实现原始消息 / 会话、记忆抽取、事实纠错、遗忘、摘要、FTS5 检索与 PromptBuilder。Phase 3 才完成对话 JSON 协议、业务表现状态机和最终陪伴交互；Phase 4 实现正式 VoiceService、分句和音频队列；Phase 5 完成桌宠输入、快捷键与 Agent Tools。现有技术验证能力保留，本阶段不扩展这些业务系统。

已按 **1A → 1B → 1C → 1D** 顺序实施，每个检查点完成后写入开发日志并报告，再推进下一个检查点。已有冻结 Unity V7 与 Spine 继续作为基线；未自动重导用户正在修改的 Blender 制作稿。

人物称呼、persona、关系基调、最终中文字体与 Home 文案可以后续单独对齐，不阻塞 1A 的基础服务工作。正式角色对话验收前需要用户确认身份内容；本阶段短请求仅用于技术验收。
